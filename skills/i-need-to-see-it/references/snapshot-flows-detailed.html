Direct vs External VM snapshots

One running VM with one disk. Step through each flow to see where the guest's writes go and how long the guest stays frozen.

Online VMs need application-consistent snapshots

Customers back up VMs while they run. The snapshot has to be clean to restore from.

  1. 01

    Application-consistent

    The guest agent freezes the guest: apps flush their data and hold new writes.

  2. 02

    Frozen while CSI takes the VolumeSnapshots

    Direct keeps the guest frozen until every disk has its VolumeSnapshot. Each disk adds to the wait.

  3. 03 10 s

    Windows gives up after 10 seconds

    VSS holds writes for 10 seconds at most. Then its writers fail: crash-consistent only.

The thaw fails with 0x80042314, and the guest agent reports "fsfreeze is limited up to 10 seconds". Every extra disk pushes the freeze further past the limit.

The idea: freeze only to switch the disks

  1. Freeze, switch, thawOne libvirt call puts every disk on a qcow2 overlay.guest frozen
  2. VolumeSnapshotsCSI snapshots the base disks, which no longer change.guest running
  3. Merge backBlock commit copies the overlays into the base disks.guest running

One test run: 319 ms frozen. VMware does the same with delta disks.

The guest should stay frozen as long as the hypervisor needs, not as long as the storage needs.

      How to ask for it

      Set snapshotMode: External on the VirtualMachineSnapshot. Without the field, snapshots keep using Direct.

      overlayScratchSize is optional and is accepted only with External mode. External mode is Alpha and needs the ExternalVMSnapshot feature gate.

      vmsnapshot.yaml
      apiVersion: snapshot.kubevirt.io/v1beta1
kind: VirtualMachineSnapshot
metadata:
  name: my-vm-snap
spec:
  source:
    apiGroup: kubevirt.io
    kind: VirtualMachine
    name: my-vm
  snapshotMode: External
  overlayScratchSize: 10Gi  # optional

      Both flows start by freezing, while the guest flushes cached data to disk. Direct then keeps the guest frozen through the whole CSI snapshot. External keeps it frozen for one libvirt call. On Windows, VSS can keep a guest frozen for at most 10 seconds.

      Everything the feature adds, object by object

      What you can see with kubectl get -o yaml and kubectl get events. The first group is the snapshot itself, the second what crash recovery adds and what it reads before it starts a VM. The step buttons jump to where each one appears; press Y on any step for the objects' YAML.

      The snapshot: what External mode adds

      Set while a snapshot runs, from the scratch PVC to the merge back. Most of it is gone again when the snapshot is done.

      VirtualMachineSnapshot

      snapshot.kubevirt.io/v1beta1
      spec.snapshotMode
      Direct (the default) or External. External needs the ExternalVMSnapshot feature gate, which is Alpha, and UtilityVolumes.
      spec.overlayScratchSize
      Optional size of the scratch PVC. CEL rules: only with External, and greater than zero. Without it: min(failure deadline × 125 MiB/s × 2, disks × 1.1).
      status.error.message
      "the overlays were gone before the snapshot completed", "Source VM stopped before snapshot capture completed", "Source VM was deleted before snapshot capture completed", or "external mode needs a running guest agent on the source of …".
      VirtualMachineSnapshotContent
      status.snapshotMode
      The mode the flow actually ran with.
      status.creationTime
      In External mode written only once every VolumeSnapshot is readyToUse, while the overlays still protect the base images. The snapshot succeeds here, before the merge back.

      VirtualMachineInstance

      kubevirt.io/v1
      condition OverlaySnapshotActive
      Projected by virt-handler from the launcher's domain metadata. Absent means no overlay transaction since this VMI started.
      reasons OverlayPreparing→OverlaysReady→OverlayCommitting→OverlayCommitted failuresOverlayCommitFailedOverlaySnapshotFailed
      status.snapshotOverlayPVCUID
      The scratch PVC the launcher's report was verified against. The controller trusts the condition only when it matches.
      spec.utilityVolumes[] type SnapshotOverlay
      The scratch PVC, attached next to MemoryDump and Backup utility volumes.
      condition LiveMigratable=False
      Reason SnapshotOverlaysNotLiveMigratable while overlays are prepared or active.
      annotation snapshot.kubevirt.io/overlay-reference
      JSON {contentUID, scratchPVCUID}, written right before the switch to overlays. The launcher's report counts only for this transaction.

      VirtualMachine

      kubevirt.io/v1
      status.snapshotInProgress
      Existing field, set as before while the snapshot runs. Cleared when the merge back is verified, or when the source VMI ends.

      Scratch PVC

      snap-scratch-<content UID>
      finalizer snapshot.kubevirt.io/overlay-protection
      Keeps the PVC, and the overlays on it, until the commit is verified. Created with it, together with an owner reference to the content and the owner-vmi-uid annotation.
      attachment pod hp-volume-*
      The usual hotplug attachment pod. The launcher sees the PVC under /var/run/kubevirt/hotplug-disks/.
      overlay files ovl-<volume>.qcow2
      One per disk, backing file set to that disk's base image. Deleted at the pivot, so an overlay exists only while its disk needs it.

      virt-launcher

      libvirt domain metadata
      <snapshotOverlay>
      KubeVirt metadata in the domain XML: phase, contentUID, scratchPVCUID, message. The phases are the condition reasons above.
      usage monitor
      Commits early when the scratch PVC reaches 70 % usage, so the overlays never run out of space.
      pause
      Each pivot pauses the guest for one libvirt call. The VMI shows a short Paused=True flicker.

      Events

      kubectl get events
      SuccessfulOverlayScratchVolumeCreate
      On the VMSnapshot when the scratch PVC is created.
      OverlayCommitFailed
      Warning: the block commit failed. The overlays stay, the scratch PVC stays protected, and the snapshot controller asks for the commit again.

      What is refused while overlays are active

      admission and subresources
      disk and volume changes
      "Cannot change disks or volumes while snapshot overlays are prepared or active" (hotplug admitter).
      addvolume, removevolume
      "VMI … has disks on snapshot overlays".
      volume migration
      "cannot migrate the volumes of …, its disks are on snapshot overlays".
      live migration
      Blocked through LiveMigratable=False, see the VMI card.

      Crash recovery: what it adds, and what it reads

      A launcher that dies with overlays leaves a protected scratch PVC and a blocked VM. No new field, no new object: the next start of the VM reads what the snapshot left behind, and refuses when any identity check fails.

      VirtualMachine

      kubevirt.io/v1 · the block, and the way out
      condition ManualRecoveryRequired
      Reason UncommittedOverlays. Set by the VM controller when a VMI that carried overlay state ends with its launcher gone and no settled report: OverlaySnapshotActive is not OverlayCommitted or OverlaySnapshotFailed for the scratch PVC in snapshotOverlayPVCUID. The message names the scratch PVC and says that starting the VM recovers the writes. Removed by the snapshot controller once the commit is verified.
      start subresource, run strategies
      A start is the recovery. virtctl start is refused only for other ManualRecoveryRequired reasons. Always and RerunOnFailure VMs restart on their own, so they recover with nobody watching; Manual and Halted VMs stay blocked until someone starts them.
      printableStatus
      Starting while the replacement VMI recovers its overlays, Running once the domain is up.
      annotation snapshot.kubevirt.io/overlays-committed
      The manual path, for when recovery is refused: commit the overlays by hand, then set the annotation to the scratch PVC's UID. The snapshot controller releases the scratch PVC and clears the block.
      a completed restore
      A VirtualMachineRestore newer than the snapshot also clears the block (restore.kubevirt.io/lastRestoreUID changed), at the price of every write newer than that snapshot.

      VirtualMachineInstance, the replacement

      kubevirt.io/v1 · created by the VM controller
      annotation snapshot.kubevirt.io/pending-overlay-recovery
      The scratch PVC name the new VMI recovers. virt-handler holds the domain start until that volume is in spec.utilityVolumes, checking every second: the domain must not start on the base images the overlays still shadow.
      annotation snapshot.kubevirt.io/overlay-reference
      The same {contentUID, scratchPVCUID} the crashed VMI carried, so the new launcher's report is checked against the same transaction.
      both annotations are immutable
      The VMI update admitter refuses any change: "modification of the snapshot.kubevirt.io/… annotation on a VMI object is prohibited".
      spec.utilityVolumes[], patched in after the create
      "cannot create VMI with utility volumes in spec, utility volumes can only be added via hotplug", so the VM controller adds the scratch volume right after creating the VMI, with a JSON patch that tests the VMI's UID.
      status.phase
      Scheduled while virt-handler waits for the scratch volume, Running once the domain is up on the overlays.
      condition OverlaySnapshotActive
      True · OverlayCommitting from the first report, message "recovering the overlays of an interrupted external snapshot"; snapshotOverlayPVCUID is set once the report matches the reference.

      Scratch PVC, protected

      snap-scratch-<content UID> · what makes it a candidate
      the identity checks
      A controller owner reference to a VirtualMachineSnapshotContent, the name snap-scratch-<that content's UID>, and the overlay-protection finalizer. The VM controller lists the namespace's PVCs from its cache and confirms each candidate with one live GET of the content: it must exist, have that UID, and name this VM as its source.
      annotation snapshot.kubevirt.io/owner-vmi-uid
      The VMI whose launcher holds the overlays. Written when the PVC is created; moved to the replacement VMI with a JSON patch that tests the PVC's UID, finalizers and resourceVersion, so a concurrent change fails the patch rather than the data.
      metadata.deletionTimestamp
      A scratch PVC being deleted is never recovered: the start is refused.
      release
      After the verified commit the snapshot controller removes the finalizer, unplugs and deletes the PVC. Without a verified commit it is released only on the manual path, with the SnapshotOverlayDataDiscarded warning.

      VirtualMachineSnapshotContent, read only

      snapshot.kubevirt.io/v1beta1 · what the controller checks
      metadata.uid, spec.source.virtualMachine.metadata.uid
      The content must be the scratch PVC's controller owner and name this VM, by UID, as its source. A content that is gone means nothing to recover.
      spec.source.virtualMachine.spec.template.spec.volumes[]
      Every PVC or DataVolume volume of the snapshotted VM must still use the same claim in the VM today, matched by volume name. A volume moved to another PVC refuses the recovery.
      spec.volumeBackups[].persistentVolumeClaim.metadata.uid
      Each backed-up PVC must still exist with the recorded UID and not be deleting. A PVC recreated under the same name refuses the recovery: the overlay's backing file would not be the disk it was taken of.

      virt-launcher

      before the domain is defined
      the overlay checks
      Each ovl-<volume>.qcow2 left on the scratch volume must be qcow2 and have exactly that disk's source as its backing file, a file or a block device. A disk with no overlay was committed before the crash, since overlays are deleted at the pivot. An overlay that belongs to no disk of the VMI refuses the start: its writes would be lost.
      the domain disk
      The disk's original source, type and format move into <backingStore>; the active layer becomes the overlay file, driver qcow2.
      <snapshotOverlay> set to OverlayCommitting before the start
      With the message "recovering the overlays of an interrupted external snapshot", so nothing captures the base images the recovery is about to write. Log line: "Starting the domain on the overlays left on scratch volume …".
      the commit
      Once the domain runs, the launcher starts the same active block commit a snapshot ends with. The snapshot controller sees a running replacement VMI, waits for OverlayCommitted for the scratch PVC's UID, retries OverlayCommitFailed, and only then releases the scratch PVC.

      Events

      kubectl get events
      FailedCreate on the VM
      "Not starting the virtual machine: the snapshot overlays cannot be recovered: …" with the reason, see below. "Error recovering the snapshot overlays: …" when the hotplug patch or the owner move fails; that one is retried on the next pass.
      SnapshotOverlaysMissing on the VM
      "Scratch PVC … was deleted before its overlays were committed": a VMI was waiting to recover a scratch PVC that is gone. The recovery context is dropped.
      SnapshotOverlayDataDiscarded on the content
      "Discarding scratch PVC … without a verified commit for VM …. Retained base PVCs may be missing writes.": the manual path released the PVC.

      When recovery is refused

      the VM stays blocked, the manual path applies
      the VM controller, before the VMI exists
      "both snap-scratch-… and snap-scratch-… hold overlays of the VM" · "scratch PVC … is being deleted" · "snapshot content … has no VM template" · "volume rootdisk no longer uses PVC rootdisk" · "PVC rootdisk was replaced or is being deleted". No VMI is created; the FailedCreate event carries the sentence.
      virt-launcher, before the domain starts
      "overlay … does not belong to volume …: format …, backing …, expected …" · "overlay … belongs to no disk of the VMI" · "volume … has no disk driver". The start fails and nothing is written to the base images; the VMI ends, the block is set again, and the VM's start-failure backoff retries.
      then
      Commit the overlays by hand and set snapshot.kubevirt.io/overlays-committed to the scratch PVC's UID, or restore a completed snapshot and accept losing the writes newer than it.
